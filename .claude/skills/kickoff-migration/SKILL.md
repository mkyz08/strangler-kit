# kickoff-migration

`docs/00_migration_plan.md` の Phase 1（現状分析・全体棚卸）を実行する。`legacy/` にレガシーソース一式が
配置されていることを前提とする。配置されていなければユーザーに確認し、中断する。

## 実行手順

1. `CLAUDE.md` と `docs/00_migration_plan.md` を読み込む。

2. `legacy/` 配下を俯瞰し、以下を把握する（Explore的な広い探索。深い業務ロジック解析は個別画面移行時に
   `legacy-analyzer` が行うため、ここではアーキテクチャ・構成の把握に留める）。
   - ディレクトリ構成、レイヤー構成（Controller/Service/Repository等の配置ルール）
   - 画面（Controller/JSP or Thymeleafテンプレート単位）の一覧
   - 認証・認可の実装方式（セッション管理、ログイン処理、権限チェックの仕組み）
   - DB接続方式・使用DB製品・主要テーブル
   - バッチ処理・帳票出力・外部連携など、画面を伴わない機能の有無
   - 共通部品（共通レイアウト、共通バリデーション、共通例外処理）
   - 使用しているCSSフレームワーク・UIライブラリ（Bootstrap等）の有無（`scaffold-foundation`で
     「現行踏襲」を選択肢として提示するために必要）

3. 画面を一つずつ洗い出し、`docs/screens_inventory.md` に以下を記入する。
   - SCR-ID（3桁連番で新規採番）
   - 画面名
   - 現行ソースの主要ファイル
   - Wave（`docs/00_migration_plan.md` §4 のWave定義を目安に、リスク・依存関係から判断）
   - 優先度
   - ステータスは全て「未着手」で初期化

   1つのControllerが一覧/詳細/編集など複数の画面（URL・業務目的が異なるもの）を提供しているケースでは、
   ユーザー操作単位で画面を分割し、それぞれ別のSCR-IDを採番する。逆に1つの業務操作が複数リクエストに
   またがるだけ（同一画面内のタブ切り替え等）であれば1画面として扱う。判断に迷うものはリストにその旨を
   備考として残し、最終的な粒度をユーザーに確認する。

4. 把握した現行アーキテクチャ概要を `docs/01_legacy_architecture_overview.md` として新規作成する
   （構成、認証方式、DB、バッチ/帳票の有無、共通部品、使用CSSフレームワーク、画面一覧へのポインタを記載）。

5. `docs/00_migration_plan.md` §11「未確定事項」のうち、今回の調査で判明したものにチェックを入れ、
   判明した内容を追記する（DB種別、認証方式など）。判明しなかったものは残し、ユーザーへの確認事項として
   最後にまとめて提示する。

6. 最後に、画面数・Wave分けの概要・未確定事項の残数をユーザーに報告し、次のSKILL
   `scaffold-foundation`（共通基盤構築）に進んでよいか確認する。**Wave 1の `migrate-screen` は
   `scaffold-foundation` 完了後に開始する**（認証方式・共通APIクライアント等を画面ごとに場当たり的に
   決めないため）。

## 注意事項

- `legacy/` は参照のみ。変更しない。
- この段階で個々の画面の詳細な業務ロジックまで深掘りしない（それは `migrate-screen` 内の `legacy-analyzer` の役割）。
  棚卸の粒度を超えて時間をかけすぎないこと。
