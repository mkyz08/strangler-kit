# handover-migration

`docs/screens_inventory.md` の全画面が「完了」になった後、プロジェクトの最終ステップとして、開発・保守
担当者向けの引き継ぎドキュメント `docs/03_handover.md` を作成する。既存の設計書群（`00`〜`02`、
`docs/screens/`配下）はAIエージェント間の作業用ドキュメントとしての性格が強く、後任の人間エンジニアが
最初に読むべき「地図」が無い。本SKILLはその地図を作る。

専用のサブエージェントは使わない。`kickoff-migration`/`scaffold-foundation`と同様、プロジェクト全体を
横断し1回限り実行するタスクであり、既存ドキュメントの要約・集約が中心（1画面分の深いコード解析を行う
`legacy-analyzer`等とは性質が異なる）ため、オーケストレーター（メインエージェント）が直接作業する。

## 実行手順

0. **前提確認（全画面完了判定）**: `docs/screens_inventory.md` が存在しない場合、`kickoff-migration`が
   未実施の可能性が高いためユーザーに確認し中断する。存在すれば「画面一覧（Wave別）」表を読み、
   全行の「ステータス」列が「完了」になっているか確認する（「対象外（画面ではない）」表の項目は
   ステータス管理対象外のため無視してよい）。
   - 未完了の画面が1件でもあれば、該当SCR-ID・画面名・現在のステータスを一覧にしてユーザーに提示し、
     「引き継ぎドキュメントは全画面完了後に作成するのが原則だが、このまま作成してよいか（例:
     一部画面を後回しにして先行リリースする場合等）」を確認する。**ユーザーが明示的に続行を指示しない
     限りここで中断する。** 続行する場合は、`docs/03_handover.md`の§0・§1・§5に未完了画面がある旨を
     明記する。

1. 以下の既存ドキュメントを一通り読み込む（存在しなければスキップし、最終報告にその旨を含める）。
   - `CLAUDE.md`、`docs/00_migration_plan.md`
   - `docs/01_legacy_architecture_overview.md`
   - `docs/02_foundation_design.md`
   - `docs/screens_inventory.md`
   - `docs/screens/<SCR-ID>_<画面名>/06_checklist.md`（全画面分。特に「未解消の指摘事項」表。
     個別画面の`06_checklist.md`が欠けている場合はその画面をスキップし最終報告に記載する）
   - `backend/pom.xml`（または`build.gradle`）、`frontend/package.json`の`scripts`、`docker-compose.yml`
     （実際の起動コマンド・ポート番号・DBコンテナ名を正確に記載するため。設計書の記載を鵜呑みにせず
     実ファイルで裏取りする）

2. **アーキテクチャ概要の作成**: `docs/02_foundation_design.md`・`docs/01_legacy_architecture_overview.md`
   を基に、フロント/バック/DB構成図（Mermaid記法可）と技術スタック一覧（現行→移行後の対比表）を作る。

3. **ローカル環境構築・起動手順の作成**: `docker-compose.yml`・`backend/pom.xml`（or `build.gradle`）・
   `frontend/package.json`を実際に読み、机上の推測ではなく実ファイルに基づいた正確なコマンド列
   （例: `docker compose up -d` → `cd backend && mvn spring-boot:run` → `cd frontend && npm install && npm run dev`）
   を記載する。可能であれば実際に起動して疎通確認する（`scaffold-foundation`ステップ7と同じ考え方。
   必須ではないが、記載コマンドが実際に動くことの検証として推奨）。ポート番号、初期認証情報
   （認証機能がある場合）、テストの実行方法（単体テスト・`npm run test:e2e`）も含める。

4. **主要設計判断のサマリ作成**: `docs/02_foundation_design.md`の各章（特に§0の一括確認事項）から、
   CSS方針・認証方針・多言語対応方針・DB方針等の主要決定と理由を簡潔に要約する。**全文転記ではなく要約**
   とし、詳細は`docs/02_foundation_design.md`本体への参照リンクに留める（内容の二重管理を避けるため）。

5. **画面一覧・移行状況の作成**: `docs/screens_inventory.md`の内容を要約する（Wave別画面数、SCR-ID一覧、
   各画面フォルダへのポインタ）。表そのものを複製せず、`docs/screens_inventory.md`本体を参照させる。

6. **既知の制約・未解決事項の集約**: 全画面の`06_checklist.md`「未解消の指摘事項」表を横断的に確認し、
   「対応状況」が「対応済み」でないものを抽出して一覧化する（SCR-ID、指摘内容の要約、詳細へのリンク）。
   さらに以下の2種類に分けて整理する（性質が異なるため）。
   - **未解決の指摘事項**（人間の追加確認・対応が望ましいもの。例:「DB照合順序の実機検証未実施」）
   - **意図的に許容した制約・スコープ外事項**（`docs/00_migration_plan.md` §3.3の例外規定や
     `scaffold-foundation`での決定に基づき、対応しないと確定済みのもの。例:「認証機能は新規追加しない」
     「IDORチェックは現行踏襲で追加しない」）
   複数画面にまたがる同一論点で既に「対応済み」となったものは集約対象外とする。

7. **修正時の参照先の整理**: `CLAUDE.md`（進め方の大原則、コーディング規約）、`docs/screens/<SCR-ID>_<画面名>/`
   の各ファイルの役割、既存SKILL（新規画面追加時は`migrate-screen`、実装修正後の再検証は`verify-migration`
   がそのまま流用できる旨）を、修正・追加開発を行う後任者向けに簡潔に案内する。

8. `docs/templates/handover_template.md`の様式に従い`docs/03_handover.md`を新規作成する。既に存在する
   場合は全文を作り直さず、「再実行時の扱い」（後述）に従い差分更新する。

9. 作成後、`CLAUDE.md`の冒頭サマリと§10更新履歴に、引き継ぎドキュメント作成完了・`docs/03_handover.md`
   への参照を追記する。

10. 作成した`docs/03_handover.md`の章立てと未解決事項の件数をユーザーに報告する。これがプロジェクトの
    最終成果物であるため、記載に過不足がないか（特に既知の制約の記載漏れ）ユーザー自身の確認を推奨する
    旨を伝える。

## 再実行時の扱い（ドキュメントの鮮度）

`docs/03_handover.md`は作成時点のスナップショットである。全画面完了後もバグ修正・追加リリース対応等で
`docs/02_foundation_design.md`や`06_checklist.md`が更新されることがあるため、以下の運用とする。

- 原則7「ドキュメントの一貫性維持」に従い、`docs/02_foundation_design.md`や`06_checklist.md`を変更した
  エージェント・人間は、その変更が`docs/03_handover.md`の該当箇所（§4主要設計判断、§6既知の制約）に
  影響するか確認し、影響する場合は該当箇所を直接更新する（全文再生成は不要。差分箇所のみ修正）。
- 本SKILLを再実行する場合、ステップ1〜7を再実施したうえで既存の`docs/03_handover.md`との差分のみ更新し、
  §8変更履歴に「何が・なぜ変わったか」を追記する。
- `docs/03_handover.md`冒頭（§0）に「作成日」「最終更新日」「元にした各ドキュメントの更新日」を明記し、
  読者が鮮度を自己判断できるようにする。

## 注意事項

- このSKILLは新しい設計判断を行わない。既存ドキュメントの要約・集約に徹する（矛盾を発見した場合は
  原則7に従い上流ドキュメント側を修正するが、本SKILL独自の判断で仕様を決めない）。
- `docs/screens/`配下の詳細設計書を要約時に改変しないこと（参照・引用のみ）。
- 全画面完了前に実行する場合（ステップ0で続行を選んだ場合）、未完了部分がある旨をドキュメント内に
  明記し、後日の更新が必要であることを明示する。
