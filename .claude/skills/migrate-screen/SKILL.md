# migrate-screen

指定された1画面（`$ARGUMENTS` にSCR-IDまたは画面名）について、`docs/00_migration_plan.md` §5 の
標準ワークフローをオーケストレーションする。あなた（メインエージェント）がこのSKILLの実行主体であり、
各ステップで該当のサブエージェントを `Agent` ツールで呼び出す。エージェント自身が他のエージェントを
呼び出すことはできないため、ステップ間の橋渡しは必ずメインスレッドが行うこと。

事前に `CLAUDE.md` と `docs/00_migration_plan.md` を未読であれば読み込むこと。

## 実行手順

0. **前提確認**: `docs/02_foundation_design.md` が存在しない場合、SKILL `scaffold-foundation`
   （共通基盤構築）が未実施の可能性が高い。認証方式・状態管理方針が未確定のまま画面移行を進めると
   後戻りが大きいため、先にユーザーに `scaffold-foundation` の実行を確認する。
   存在すれば、`docs/screens_inventory.md` から対象のSCR-IDと画面名を特定する（存在しない場合は
   ユーザーに確認し、勝手に採番しない）。画面フォルダ `docs/screens/<SCR-ID>_<画面名>/` を作成する。

1. **現状分析**（該当ファイルが未作成の場合のみ）: `legacy-analyzer` エージェントを呼び出し、
   `01_legacy_analysis.md` を作成させる。`docs/screens_inventory.md` のステータスを「分析中」→完了後「設計中」に更新する。

2. **画面設計**: `screen-designer` エージェントを呼び出し、`02_screen_design.md` を作成させる。

3. **API設計**: `api-designer` エージェントを呼び出し、`03_api_design.md`（必要なら `04_db_design.md`）を作成させる。

4. **設計レビュー（人間承認ゲート）**: ここで一旦停止する。作成した設計書一式のサマリと、各設計書の
   「未確定事項」を整理してユーザーに提示し、承認を求める。**ユーザーの明示的な承認を得るまで次のステップに進まない。**
   差し戻しがあれば該当エージェントを再実行する。承認が得られたら `docs/screens_inventory.md` のステータスを
   「実装中」に更新する。

5. **実装**: `backend-coder` と `frontend-coder` を呼び出す（互いに依存しないため並列実行してよい）。
   両者からの報告（設計書との差異の指摘等）を確認し、あれば対応方針をユーザーに確認する。

6. **検証**: `docs/screens_inventory.md` のステータスを「テスト中」に更新した上で `test-engineer` を呼び出し、
   `05_test_spec.md` を作成させる。現新比較検証で不一致が見つかった場合、実装不備であれば該当コーダーに
   差し戻し、意図的な仕様変更であれば設計書側の記載が十分か確認する。

7. **レビュー**: ステータスを「レビュー中」に更新し `migration-reviewer` を呼び出す。指摘事項があれば
   該当ステップに差し戻す。

8. **リリース判定（人間承認ゲート）**: ステータスを「リリース判定待ち」に更新し、`06_checklist.md` の内容と
   検証結果のサマリをユーザーに提示して最終承認を求める。**このステップもユーザーの明示的な承認が必須。**

9. 承認後、`docs/screens_inventory.md` のステータスを「完了」に更新して終了報告する。

## 注意事項

- 各ステップの成果物は必ず対応するテンプレート（`docs/templates/`）の様式で作成されていることを確認する。
- ステップ4・8以外は基本的に連続実行してよいが、致命的な矛盾や未確定事項が多い場合は都度ユーザーに判断を仰ぐ。
- 実行中の進捗（今どのステップか、次に何をするか）を都度ユーザーに簡潔に共有する。

## 複数画面をバッチで進める場合

ユーザーが複数画面をまとめて進めることを希望した場合、画面ごとに個別のゲートで止めるのではなく、
同種のステップ（例: 複数画面のステップ1を並列実行）をバッチ化し、ゲート（ステップ4・8）もまとめて
1回の確認にしてよい。その場合、以下に注意する。

- **ステップ1〜3、5〜7は画面間で独立**なので`Agent`ツールを同一メッセージ内で複数回呼び出し並列実行してよい。
  ただしステップ6（結合テスト）で複数の`test-engineer`が同時に`mvn spring-boot:run`等でバックエンドサーバーを
  起動しようとすると、ポート・共有DBが競合する。**メインスレッドが1回だけ実機起動して全画面分の疎通確認を
  まとめて行い、その結果を各`test-engineer`に転記材料として渡す**（各エージェント自身のサーバー起動は避ける）。
- ステップ5で複数画面が`GlobalExceptionHandler.java`・`router.tsx`・`menuConfig.ts`のような共有ファイルを
  同時に編集することがある。実装完了後、メインスレッドが該当ファイルを直接確認し、全画面分の変更が
  欠落なく残っているか検証する（`grep`等で該当シンボルの存在を確認する程度でよい）。
- バッチ完了後、画面をまたいで共通する指摘（設計書間の命名不一致、ドキュメントの記載漏れ等）があれば、
  次のバッチに活かせるよう`docs/00_migration_plan.md`に知見として記録する。
